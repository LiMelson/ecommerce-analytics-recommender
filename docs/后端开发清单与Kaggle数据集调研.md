# 后端开发清单与 Kaggle 数据集调研

整理日期：2026-11-15。适用项目：电商平台用户行为分析与精准推荐系统。

2026-11-16 实施更新：本文保留数据集调研与早期计划。当前已实现 FastAPI + MySQL + ClickHouse、账号权限、导入任务、统计画像等，最新状态见 [项目首页](../README.md)；实际接口见 [接口文档](接口文档.md)，不再使用下文早期“尚未实现”描述判断当前工程。数据清洗和训练仍由对应负责人实现。

本文件按最新讨论收敛首版范围：保留现有 Vue 前端，重点完成真实行为数据、推荐算法实验和模型接入。算法与训练参数由开发团队固定，网站操作人员只选择匿名用户并查询推荐。本文不代表后端、数据导入或真实训练已经实现。

## 一、现有工程的实际状态

- 首页、大屏、趋势、漏斗、RF 分群、留存、排行和画像已有展示与浏览器计算逻辑。
- 当前样本为程序生成，CSV 导入、留言、账号和日志仅保存在当前前端会话中。
- `frontend/src/App.vue` 的 `generateRecommendation` 调用本地规则，`startTraining` 模拟任务状态；当前没有真实推荐接口、数据库或训练模型。
- 当前页面仍有策略选择与训练参数弹窗。后续接入时按最新要求移除这些选择；参数改为服务端配置。不要将原型的 BPR 文字视为已完成 BPR 训练。

## 二、首版需要补充的后端

| 模块 | 核心交付 | 页面或用途 |
|---|---|---|
| 数据处理与存储 | 数据源适配、类型和时间校验、清洗报告、行为明细存储、数据集版本 | 导入、查询、导出及所有计算的基础 |
| 统计与画像 | 日/小时聚合、严格漏斗、样本首现留存、RF 分群、商品和类目排行、用户兴趣与历史摘要 | 首页、大屏、七个分析页、用户画像 |
| 离线训练与实验 | 固定配置运行热门推荐、ItemCF、BPR；统一时间切分、负采样和评估；记录配置与结果 | 选择最终模型，形成课程实验报告 |
| 模型管理与推荐 | 保存模型、ID 映射和训练数据版本；加载兼容的活动模型；返回默认 Top10；热门兜底 | 智能推荐页面 |
| 最小系统支撑 | 配置、错误处理、基础认证、必要操作日志、启动说明与数据库初始化 | 联调、部署与可重复演示 |

完整角色权限编辑、留言管理、个人资料修改和复杂审计筛选可以在推荐闭环稳定后补齐。首版采用 Python API、MySQL、CSV/Parquet 文件和独立训练脚本即可；Redis、分布式平台和复杂任务队列按实测需要再引入。

### 推荐的开发顺序

1. 确定一个主数据集，将字段和行为类型转换为统一格式。
2. 用固定小样本核对统计，再接通首页与用户列表，确认前端可以查询真实结果。
3. 跑通热门推荐与 ItemCF，建立时间划分下的实验基线。
4. 训练 BPR，比较 Recall@10、NDCG@10、覆盖率和查询耗时；在验证集选定配置。
5. 保存模型、ID 映射、数据版本与评估报告，接入推荐页面；刷新与服务重启后仍能恢复。
6. 接入其余分析页面，再完善辅助管理模块。

训练初期可以由开发者执行脚本，无需先开发网站训练接口。以后如保留“重新训练”，只允许管理员触发服务端固定配置，训练在独立进程运行，查询接口不等待训练完成。

## 三、建议的最小接口

统一前缀 `/api/v1`。下表为待团队定稿的接口建议，尚未实现。

| 方法与路径 | 主要输入 | 主要输出 |
|---|---|---|
| `GET /overview` | 可选数据版本、日期范围 | KPI、趋势、行为量与实际数据版本 |
| `GET /analytics/{metric}` | daily、hourly、funnel、rf、retention、category、product 等指标与筛选 | 同源图表数据及明细 |
| `GET /users` | 搜索、分页、可选数据版本 | 可选择的匿名用户列表 |
| `GET /users/{user_id}/profile` | 用户 ID、可选数据版本 | 行为构成、RF、兴趣类目和历史摘要 |
| `GET /recommendations` | 用户 ID | 商品、类目、可选相对指数、真实推荐依据和实际模型版本 |
| `GET /behaviors` | 用户/商品、类型、时间、分页 | 原始行为查询结果 |
| `GET /models/active` | 无或指定数据版本 | 活动模型、训练范围、配置摘要与评估结果 |
| `POST /datasets/import` | 文件、字段映射、时区 | 导入状态与数据版本；较大任务异步处理 |

网站默认采用服务器选定的数据与模型版本，前端不提供算法或参数选择；调用者显式指定版本时仍须校验兼容性。请求 ID、统一错误、分页上限、鉴权和日期格式在公共约定中统一。

大数据文件可以先由开发者在服务器导入；现有浏览器上传限制为 10 MB、25,000 行，不应为了训练全量数据而将数百万行加载到网页中。

## 四、数据集核验方式与结果

已读取发布者的 Kaggle 数据说明、公开 API 元数据及文件清单，并分别读取一个文件开头的压缩字节范围进行小样本检查。三个请求均返回 HTTP 206，每个读取 262,144 字节，共约 0.75 MiB 压缩数据；不代表已下载全量或完成全量质量统计。

| 数据集 | 官方声明的范围 | 文件抽查结果 | 本项目判断 |
|---|---|---|---|
| Retailrocket recommender system dataset | 约 4.5 个月，2,756,101 条事件，1,407,580 位访客 | `events.csv` 约 21,270 条完整样本记录中确认 view、addtocart、transaction | 首版优先候选；行为表较小，但购买稀疏，类目要关联商品属性表 |
| eCommerce Events History in Cosmetics Shop | 2019-10 至 2020-02，发布者称约 2,000 万条事件 | `2019-Oct.csv` 约 13,145 条样本中确认 view、cart、remove_from_cart、purchase | 字段更丰富，适合多行为及会话实验；建议先处理一个月或固定用户子集 |
| eCommerce behavior data from multi category store | 发布者描述整个系列为 2019-10 至 2020-04、约 2.85 亿条事件 | `2019-Oct.csv` 约 7,857 条样本中确认 view、cart、purchase | 首版规模偏大；当前 Kaggle 文件清单只有 2019 年 10 月、11 月，更多月份由作者站另行提供 |

抽查只证明样本中存在相应类型，不能用其比例代替完整数据分布。REES46 的数据说明中 `event_type` 字段表与后文事件列表有不一致，以上行为类型已通过文件样本核实。

### 1. RetailRocket：建议先用它跑通闭环

Kaggle：https://www.kaggle.com/datasets/retailrocket/ecommerce-dataset

发布者声明数据来自真实电商站点，保密字段经过哈希处理。行为表使用访客和商品标识，不含姓名、手机号字段。事件表结构为：

```text
timestamp,visitorid,event,itemid,transactionid
```

- 行为：`view` 浏览、`addtocart` 加购、`transaction` 购买/交易事件。
- 官方说明列出 2,664,312 次浏览、69,332 次加购、22,457 次交易事件。交易事件数量不是直接去重后的订单数。
- `events.csv` 元数据大小为 94,237,913 字节，约 94 MB；完整数据还包括两个商品属性文件及类目树，未压缩文件合计约 987 MB。
- 类目不在事件表中，需要从 `item_properties_part1/2.csv` 中取 `categoryid` 属性；属性带时间，训练特征与历史统计按事件或预测时刻做关联，不能直接使用未来属性。
- 商品文本与多数属性经过处理，不适合直接展示真实商品名称、图片或假定有可解释成交金额。现有 RF 页面可以继续使用。
- 购买信号相对稀疏，应报告有效评估用户、冷启动用户与被过滤记录；过滤规则在训练窗口确定，不用测试集结果反复筛选用户。
- Kaggle 当前许可字段标注为 `CC BY-NC-SA 4.0`。交付中保留数据来源和相应许可信息。

### 2. 化妆品店行为：字段更丰富的备选

Kaggle：https://www.kaggle.com/datasets/mkechinov/ecommerce-events-history-in-cosmetics-shop

数据来源为 REES46/Open CDP。字段包括：

```text
event_time,event_type,product_id,category_id,category_code,brand,price,user_id,user_session
```

发布版以用户 ID、商品 ID 与会话 ID 记录行为，文件头不含姓名或手机号字段。主要优势是事件表直接包含类目、价格和会话信息；品牌和类目文本可能缺失，需要全量清洗后统计覆盖率。

- Kaggle 当前五个月文件未压缩合计约 2.43 GB；单个 `2019-Oct.csv` 约 483 MB。这里只表示原始文件规模，不表示下载包大小或训练显存需求。
- 先按固定用户集合保留所选窗口内的全部行为，避免只取文件前几万行；然后按时间切分训练、验证、测试。
- `remove_from_cart` 是移出购物车，不能映射为收藏。首版可单独保留为撤回行为，不直接当成确定的负反馈。
- 有 `price` 并不自动具备完整的订单金额、商品数量和退款口径。需要金额指标时先明确购买事件的去重与汇总规则，不能直接声称是真实 GMV 或订单消费金额。
- 发布者页面说明可以免费使用并要求注明该数据页及 REES46 来源，Kaggle 许可字段为 `Data files © Original Authors`；交付中保留原始说明与来源。

### 3. 多类目店铺：后续扩量再考虑

Kaggle：https://www.kaggle.com/datasets/mkechinov/ecommerce-behavior-data-from-multi-category-store

与化妆品数据使用同类字段，提供类目、品牌、价格和会话。当前 Kaggle 文件清单中，2019 年 10 月约 5.67 GB、11 月约 9.01 GB，未压缩合计约 14.68 GB；不能把作者整个系列的 2.85 亿条都当作 Kaggle 这两个文件的记录数。

来源站提供更多月份：https://rees46.com/en/datasets

首版不需要为了数据量而处理全部月份。若采用，先固定一个月和明确的用户样本；训练成本主要还取决于用户/商品数、候选集和算法实现，不能仅凭 RTX 4060 判断全量训练是否合适。

## 五、接入现有系统的字段映射

| 系统统一字段 | RetailRocket | REES46 化妆品/多类目 |
|---|---|---|
| `user_id` | `visitorid` | `user_id` |
| `item_id` | `itemid` | `product_id` |
| `category_id` | 从按时刻关联的商品属性取 `categoryid` | `category_id` |
| `event_time` | `timestamp`，毫秒时间戳 | `event_time`，明确为 UTC 的文本时间 |
| `behavior_type` | view → pv；addtocart → cart；transaction → buy | view → pv；cart → cart；purchase → buy；remove_from_cart 单独保留 |

用户与商品 ID 在 API 中统一作为字符串，时间保存为 UTC，界面按北京时间展示。源数据没有收藏事件时，标明“不提供收藏数据”；不能人为生成 fav 来补齐页面。

公开行为数据可用于离线训练和评估，不等于已有真实曝光日志。没有曝光记录时，不把浏览次数或购买事件比例当作真实推荐 CTR，也不声称离线指标提升等于线上成交提升。

## 六、建议结论

以 RetailRocket 作为先跑通数据、训练和推荐服务的候选，若购买正样本和字段需求评估后不合适，再选择化妆品店数据的固定子集作为主数据。不要在第一轮就并行适配多个大数据集，也不要把不同站点相同数值的用户或商品 ID 合并。

最终选择前，对全量或固定实验样本输出一次数据报告：行数、用户/商品数、行为分布、购买用户数、用户历史长度、字段缺失、重复记录、时间范围及候选可覆盖率。这样才能判断当前数据是否足以支撑购买推荐任务。
