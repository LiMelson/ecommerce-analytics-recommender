# 电商平台用户行为分析与精准推荐系统：文献调研与技术路线建议

调研日期：2026-11-14。项目约束：4 人、约 1 个月、有 NVIDIA RTX 4060；显存、系统内存及成员技术栈尚未确认。本文是开发前的调研建议，未开始实现系统，也未运行下述论文代码。

2026-11-16 范围说明：本文保留早期调研与扩展方案。当前首版范围以 [项目首页](../README.md) 和 [后端开发清单与 Kaggle 数据集调研](后端开发清单与Kaggle数据集调研.md) 为准：优先真实数据、基础推荐实验与模型接入，算法和参数由开发团队固定；在线反馈链路与复杂模型不作为首版必做。

范围更新：用户已确认采用参考截图中的后台分析平台，先实现本地前端展示。现有工程位于 `frontend/`，使用 Vue 3、Vite、ECharts；具体页面与交互以 `frontend/README.md` 为准。当前未接入后端或真实训练模型。

## 1. 调研结论

保留原项目的数据采集、清洗、分析、推荐、展示的分层思路。优先改进行为含义、时间因素、在线反馈和评估方法。Web 框架的替换本身不会提高推荐准确度。

建议把“精准”定义为：在统一的时间划分、候选商品范围、计算资源和调参预算下，推荐的排序质量优于热门推荐和基础协同过滤，并报告覆盖率、冷启动表现及接口延迟。论文里的提升不能直接作为本项目的预期提升。

建议主线：完整行为记录 → 用户行为分析 → 多路候选召回 → 多行为和时间特征排序 → 推荐展示 → 曝光、点击及购买反馈。深度序列模型作为增强实验，是否进入最终系统取决于测试结果与工程成本。

## 2. 与题目直接相关的近期资料

### 2.1 多行为推荐综述：先理解问题

- 标题：Multi-Behavior Recommender Systems: A Survey。
- 首次提交：2025-03-10；论文页面注明 PAKDD 2025 Survey Track 接收。
- 原文：https://arxiv.org/abs/2503.06963
- 内容：按数据建模、表示编码和训练方式整理多行为推荐。
- 可借鉴点：浏览、收藏、加购、购买应保留行为类型；固定权重求和只是基线。我们需要明确最终目标是点击、购买，还是下一次交互。
- 定位：用于需求分析与研究背景，不能替代工程实施文档。

### 2.2 HGIB：辅助行为也可能带来噪声

- 标题：Hierarchical Graph Information Bottleneck for Multi-Behavior Recommendation。
- 首次提交：2025-07-21；RecSys 2025 论文。
- 原文：https://arxiv.org/abs/2507.15395
- 作者代码：https://github.com/zhy99426/HGIB
- 内容：通过信息瓶颈及图结构精炼，减少辅助行为中与目标购买无关的信息。
- 复现条件：已读取作者仓库 README，包含环境、数据说明和训练命令；README 列出 Taobao、Tmall、Jdata 数据。尚未实际下载验证数据和运行训练。
- 可借鉴点：反复浏览不一定代表强购买意图；不同辅助行为的贡献应做消融实验。
- 定位：有算法基础时可作为复现候选。图数据构造和训练调试会增加一个月项目的风险，建议先完成基础系统。

### 2.3 长期偏好与短期会话融合

- 标题：Design and implementation of an e-commerce sequential recommender system based on BERT4Rec and user session enhancement。
- 出版：2026-06-04，Discover Artificial Intelligence。
- 原文：https://link.springer.com/article/10.1007/s44163-026-01554-z
- 内容：结合长期兴趣、时间感知的短期会话及门控融合；离线缓存长期表示，线上处理短期信息。
- 复现限制：主要实验使用内部日志，数据声明为合理请求后提供；本次未在正文找到作者代码仓库链接。
- 可借鉴点：历史喜欢某类商品，不等于当前正在购买它。可先用长期类目偏好与最近会话类目偏好实现简化融合。
- 定位：架构和特征设计参考，不承诺原样重现其指标。BERT4Rec 本身是既有模型，2026 年论文的新意在组合设计。

### 2.4 BLMRec：行为的有效期与购买意图

- 标题：Behavior lifetime modeling uses time sensitive behavioral signals to rank candidate items for purchase in E commerce recommendation。
- 出版：2026-10-13，Discover Artificial Intelligence。
- 原文：https://link.springer.com/article/10.1007/s44163-026-02419-1
- 内容：建模行为类型、距离预测时刻的时间、行为有效期，以及历史商品与候选商品的关系。
- 复现限制：使用 Taobao UserBehavior 和 RetailRocket；数据声明为合理请求后提供；本次未在正文找到作者代码仓库链接。
- 可借鉴点：不同类型行为设置不同时间衰减，增加最近浏览、加购后未购买、近期类目偏好等特征。
- 定位：很适合作为本项目改进思路来源。简化的时间衰减实现应称为“受其启发的方案”，不能声称复现了完整 BLMRec。

### 2.5 RecNextEval：先确保实验可信

- 标题：RecNextEval: A Reference Implementation for Temporal Next-Batch Recommendation Evaluation。
- 首次提交：2026-04-15；页面注明 SIGIR 2026 接收。
- 原文：https://arxiv.org/abs/2604.13665
- 内容：以全局时间窗口划分数据，降低未来信息泄漏，评估未来一个窗口的推荐。
- 可借鉴点：在预测时刻之前计算用户统计、商品热度、相似度、负样本范围等；不能用全量数据先生成特征再切分。
- 定位：评估协议参考。下一次交互推荐与未来窗口购买推荐是不同任务，需先选定一种主任务。

### 2.6 RecGPT-V3：持续更新的用户记忆

- 标题：RecGPT-V3 Technical Report。
- 首次提交：2026-07-17；当前所读版本修订于 2026-07-24。技术报告/预印本。
- 原文：https://arxiv.org/abs/2607.15591
- 内容：淘宝推荐中的结构化用户记忆、文本和商品语义 ID 的结合，以及推理开销优化。
- 可借鉴点：用户画像增量更新，画像可追溯到行为证据，避免每次请求处理全部历史。
- 定位：工业设计参考。大模型训练、语义 ID 和工业数据链路不适合整体照搬为一个月项目。

### 2.7 RecGroupMemory：本月发布的群体画像与反馈研究

- 标题：RecGroupMemory: Feedback-Aware Cohort Memory for E-Commerce Recommendation。
- 首次提交：2026-11-02。预印本；不能按已完成同行评议的结论使用。
- 原文：https://arxiv.org/abs/2611.02453
- 内容：将群体记忆构建与反馈修订分离，用前一天反馈调整给 LLM 的决策指导，同时保留指定原始观测。
- 适用边界：报告的线上比较针对业务选定的低购买力淘宝用户群体，不能直接推广到全部用户或我们的离线数据。
- 可借鉴点：分群策略应根据反馈更新，原始统计与自动生成的建议分开保存。
- 定位：可用于画像策略和扩展功能讨论，优先级低于推荐与评估主线。

### 2.8 MPIUR：本月发布的多模态商品推荐研究

- 标题：A Technique to Model Product Information and User Reviews (MPIUR)。
- 首次提交：2026-11-09。预印本。
- 原文：https://arxiv.org/abs/2611.13361
- 内容：联合商品文本、图片、用户评价及图结构，研究交互稀疏商品的推荐。
- 数据：Amazon Reviews 2023 的 Musical Instruments 与 Baby 类目。
- 可借鉴点：新商品和稀疏商品可利用内容信息补充行为信号。
- 定位：依赖具有真实文本、图片和评论的数据。若主数据只有匿名商品 ID 和行为日志，第一版不采用完整多模态方案。

## 3. 四人一个月的建议范围

### 必须完成

1. 前端首页与数据大屏：展示行为统计、趋势、漏斗和快捷入口。
2. 数据分析：每日/每时趋势、顺序转化漏斗、RF 分群与画像、留存、购买类目/商品排行。
3. 智能推荐：选择匿名用户、生成商品 ID 推荐列表、查看画像与推荐明细、模型任务入口。
4. 数据与系统模块：CSV 导入、查询、导出、日志、留言、账号、权限与个人信息。
5. 后续算法工作：热门推荐与 ItemCF 基线，多行为/时间改进方案，以及统一时间切分下的可复查评估。前端展示阶段不声称完成这些模型实验。

本项目不建设商品交易端，不包含购物车、订单、支付或完整商城。当前展示交互不等同于后端能力已经实现。

曝光应按约定的真实展示条件记录。没有曝光记录时，不能把“点击数/行为总数”标为 CTR。少量同学的演示操作也不足以证明商业转化提升。

### 推荐的工程结构

- 前端：若成员熟悉 Vue，采用 Vue 3 + ECharts；否则用团队熟悉的框架，避免额外学习成本。
- 业务 API：Python FastAPI 或 Flask。倾向 FastAPI 的方案需要结合团队熟悉度决定，二者均不能直接决定推荐精度。
- 业务存储：MySQL；历史行为可保留为分区 Parquet 文件，避免把全部明细反复加载进应用内存。
- 小样本处理：Pandas 或 Polars，选一种即可。
- 训练：LightGBM 排序作为可选主线；PyTorch 序列模型作为增强实验。
- 缓存：出现重复计算或响应瓶颈时加入 Redis，不作为演示前置条件。
- 部署：单机优先，能在干净环境按文档启动；有 Docker 经验时再用 Compose 统一依赖。
- Spark、Kafka、Flink、Hadoop：仅在数据规模、实时处理目标或课程要求明确时加入。

这里的技术组合是本项目的工程判断，不是上述某篇论文的原架构。

### 推荐链路

候选召回使用热门商品、ItemCF 相似商品、近期兴趣类目，合并去重后排序。排序特征包括各类行为次数、距最近行为的时间、不同窗口的兴趣、用户与候选类目的匹配、商品训练期热度及召回分数。

LightGBM 官方提供 lambdarank 与 rank_xendcg 等排序目标：https://lightgbm.readthedocs.io/en/stable/Parameters.html 。训练需定义推荐请求/用户时刻分组及未来窗口标签；采样得到的未购买样本不等于用户真实不喜欢。其输出默认作为排序分数，不直接称为真实购买概率。

如果进度和数据允许，再使用 SASRec 比较序列建模收益。SASRec 是 2018 年模型，并不是 2026 年新提出，但有成熟实现可作为对照。RecBole 官方实现文档：https://recbole.io/docs/recbole/recbole.model.sequential_recommender.sasrec.html 。不能预设深度模型一定优于轻量方法。

已浏览但未购买的商品可以保留为转化候选，不要机械地过滤所有历史交互商品；对已购买商品是否过滤取决于复购业务规则。

## 4. 数据选择的先决条件

优先核验天池淘宝用户行为数据：https://tianchi.aliyun.com/dataset/649 。下载后确认实际字段、时间跨度、授权条件、商品及用户 ID 覆盖、购买稀疏度，再确定样本量。

如果没有真实价格，不展示真实 GMV、客单价和 RFM 中的 Monetary；可改为最近购买时间、购买频次和活跃度分群。如果没有文本图片，多模态与自然语言商品理解不作为主实验。不同平台的匿名商品 ID 不能凭 ID 数值拼接。

网页演示可使用单独标注的演示商品目录和实时行为；其模型结果与历史数据集实验分别报告。若要用同一模型驱动真实商品推荐，需要可验证的目录映射和足够行为支持。

## 5. 四周里程碑与分工建议

| 时间 | 里程碑 | 验收方式 |
|---|---|---|
| 第 1 周 | 确定任务、数据和接口；跑通基础网页及热门推荐 | 登录后可查看商品并记录行为，数据样本可查询 |
| 第 2 周 | 完成行为看板、画像、ItemCF 和离线时间评估 | 图表可与原始统计核对，基线指标可复跑 |
| 第 3 周 | 完成多行为和时间特征排序；有余力做 SASRec | 与基线公平对比，消融时间和会话特征 |
| 第 4 周 | 冻结功能、集成测试、部署、截图、报告和演示 | 换环境可启动，算法与页面数据一致 |

建议分工：一人用户端与管理端页面，一人后端与行为采集，一人数据处理与分析，一人算法与评估。共同定义接口、参与代码审查和集成；不要等最后一周才合并。第 3 周结束后只修复问题，不继续增加模型。

## 6. 下一步决策

首先下载并核验主数据集，确认团队最熟悉的 Web 技术栈及实际硬件。在小样本上建立热门推荐和 ItemCF 的时间评估结果，再决定采用轻量排序、序列模型，还是两者结合。最终选择以验证集结果、资源成本和可交付性为依据，测试集只用于最终报告。
